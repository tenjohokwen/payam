L1 System Context

What Payam is, who uses it, and what external systems it depends on.

Payam is a multi-tenant mobile money payment gateway for Cameroon. It wraps the MTN MoMo and Orange Money provider APIs behind a single, provider-agnostic REST interface. Merchants integrate once via API key and can accept payments from either network without knowing which provider is handling the transaction.

The system is built as a modular monolith on Spring Boot 3 / Java 21 with PostgreSQL as the primary store, Redis for distributed coordination, and Quartz for background scheduling. There is no external message broker — inter-module events travel through Spring's ApplicationEventPublisher with a PostgreSQL-backed publication registry for durability.

Layer Convention

Every module follows the same 6-package convention, enforced by ARCHITECTURE.md:

api/            ← @RestController — entry points, request/response mapping
contract/       ← DTOs, enums, events, exceptions, value objects
service/        ← @Service — business logic and orchestration
infrastructure/ ← HTTP clients, Quartz listeners, Spring filters
repo/           ← @Entity + Spring Data @Repository
config/         ← @Configuration, @Bean, module wiring
Dependency Rule Dependency flow is strictly: api → service → repo. Infrastructure components call into service/repo. contract/ is importable from anywhere. Config is the composition root. No upward or cross-layer shortcuts are permitted.

L2 Payment Initiation

The core use case: a merchant POSTs a payment request and receives HTTP 202 within milliseconds. The actual settlement happens asynchronously via provider callback or polling.

Step Breakdown

1. Authentication (ApiKeyAuthenticationFilter)

The raw API key is hashed (SHA-256 + salt) before any DB lookup — the plaintext never persists. The filter supports a 24-hour rotation grace window: both the old ROTATED key and the new ACTIVE key are accepted simultaneously during rollover. SUSPENDED tenants are rejected with HTTP 403 at this stage — no further processing occurs.

2. Provider Routing (MsisdnRouter)

The destination mobile number prefix (e.g. 67x, 65x for MTN; 69x, 655 for Orange in Cameroon INFERRED) determines which adapter handles the payment. The mapping is driven by platform configuration, not hardcoded.

3. Idempotency Reservation

A merchant-supplied idempotencyKey is SET in Redis with NX+EX (atomic). If the key already exists, the cached response is returned immediately without re-processing. A PostgreSQL fallback handles Redis downtime (see Pitfall 8).

4. Transaction Creation

A Transaction row is created in state INITIATED and committed in its own transaction (TX1). This ensures the transaction is visible for reconciliation even if the orchestrator crashes mid-flight.

5. Fraud Scoring

Four independent velocity checks run against Redis Bucket4j token buckets: IP velocity, MSISDN velocity, application-level velocity, and household (same device fingerprint) velocity. Exceeding any threshold increments a fraud score. Above the configured threshold, the payment is rejected and a FraudEvent is published.

6. Fee Calculation

Per-tenant fee rules (fixed or percentage) are loaded from a cached rule set. The computed fee is stored against the transaction within TX2.

7. Provider Call (no active transaction)

No @Transactional here — this is intentional The HTTP call to Orange/MTN happens with no DB connection held. See L4 — Orchestrator Transaction Boundaries and Pitfall 1.

8. State Transitions

After a successful provider response, four state transitions fire in sequence within TX3: INITIATED → AUTH_PENDING → AUTHORIZED → PROCESSING. This looks redundant but is required by the state machine's enforced step-by-step transitions. See Pitfall 2.

Double-Check Pattern

Design Principle Payam never transitions a transaction to a terminal state based solely on a webhook payload. The callback acts only as a trigger to re-query the provider's status API. The provider API is the single source of truth.

This guards against two attack vectors:

  • Forged callbacks — an attacker POSTing a fake SUCCESS callback to /v1/callbacks/orange would still trigger a real status check against Orange's API, which would return PENDING or FAILED.
  • Replay attacks — the Redis dedup check (24h TTL, NX set) prevents the same callback from being processed twice even if the provider re-delivers.
INFERRED — Callback signature verification It is unclear whether Payam verifies a provider-supplied HMAC/signature on inbound Orange callbacks. The code applies dedup and double-check, but explicit signature verification of the inbound payload was not confirmed. INFERRED

Tenant Onboarding

Admin creates a tenant record. The system generates an API key pair (raw key returned once, hashed form stored). The merchant uses the raw key in X-Api-Key for all payment requests. Keys can be rotated (old key accepted for 24h) or revoked (immediately rejected). A Quartz job (RotatedKeyCleanupJob) runs every 5 minutes to revoke expired rotated keys.

INFERRED — Self-service signup Whether tenants can self-register or only admin-provisioned tenants are supported is INFERRED to be admin-only based on code structure, but not confirmed.

Admin Investigation

Admin users (JWT-authenticated) access /v1/admin/**. The admin module provides:

  • Transaction search and detail view with full Envers audit trail (who changed what, when)
  • Event log chain integrity verification (EventLogService.verifyChain())
  • Reconciliation report access
  • Alert rule management (fraud spike, failure rate thresholds, callback anomaly detection)
  • Tenant suspension/reactivation
  • Metrics dashboard backed by Micrometer counters (payment.success.total, payment.failed.total, payment.fraud.blocked.total)

L3 Transaction Module

The transaction module is the heart of Payam's reliability guarantees. It owns the state machine, idempotency, double-entry ledger, and the immutable hash-chain event log.

Transaction State Machine

TransactionStatus is an enum with an allowedTransitions() method returning an EnumSet. Calling transitionTo() with an invalid next state throws IllegalStateTransitionException. Terminal states accept no further transitions.

stateDiagram-v2 [*] --> INITIATED : TransactionService.initiate() INITIATED --> AUTH_PENDING : orchestrator step 1 AUTH_PENDING --> AUTHORIZED : orchestrator step 2 AUTHORIZED --> PROCESSING : orchestrator step 3 PROCESSING --> SUCCESS : webhook / poller (terminal) PROCESSING --> FAILED : webhook / poller (terminal) SUCCESS --> REVERSED : manual reversal (terminal) FAILED --> [*] SUCCESS --> [*] REVERSED --> [*] note right of PROCESSING : PESSIMISTIC_WRITE lock\nfor all transitions from here
Fig 3.1 — Transaction state machine (7 states, 3 terminal)
32 illegal transitions are tested The state machine test suite explicitly tests all 32 disallowed transitions. Do not add convenience transition shortcuts — the step-by-step path is required. See Pitfall 2 for the three seemingly-redundant orchestrator transitions.

Idempotency Service

Prevents duplicate payments when merchants retry a request (network failure, timeout).

Algorithm

  1. Redis NX+EX reservation — atomic SET only if not exists, with TTL. Primary path.
  2. If Redis unavailable — PostgreSQL INSERT with ON CONFLICT DO NOTHING as fallback.
  3. On a duplicate hit, the stored response is returned immediately (no re-processing).
  4. After successful processing, idempotencyService.store() persists the response for future replays.
Pitfall 8 — Redis fallback is load-bearing, not optional If Redis goes down and the PostgreSQL fallback is removed, ALL payments fail during the outage. The fallback must remain in place.

Ledger Service

Every successful payment produces exactly two LedgerEntry rows in a single atomic transaction:

EntryAccountTypeAmount
1CUSTOMER_WALLETDEBITpayment amount
2PROVIDER_CLEARINGCREDITpayment amount

Both rows share the same entryGroupId. The ledger is reconciled daily against provider reports by ReconciliationService.

INFERRED — Fee posting Whether a third ledger entry for fee revenue is posted at settlement is INFERRED to be handled separately; fee storage on the transaction record was confirmed but a corresponding ledger credit to a fee account was not explicitly verified.

Event Log (Hash Chain)

Every state transition appends an immutable PaymentEventLog row. The rows form a SHA-256 hash chain — each event stores the hash of the previous event, creating a tamper-evident audit trail.

Hash input format

{transactionId}|{status}|{timestamp}|{previousHash}

The genesis event uses the literal string "GENESIS" as previousHash. EventLogService.verifyChain() recomputes hashes from genesis and detects any modification.

The entity is marked @Immutable — Hibernate will not issue UPDATE statements for it.

Pitfall — @Immutable ≠ DB-level constraint @Immutable prevents Hibernate from issuing UPDATEs in the same session. A direct JDBC or SQL statement bypasses this. The chain integrity check is the real defence; treat it as an audit tool, not a security boundary.

Orange Money Adapter

File: orange/service/OrangeMoneyPort.java, orange/infrastructure/OrangeMoneyClient.java

Initiation sequence (provider-side)

  1. Query subscriber info — validate MSISDN is active and capable of payments
  2. POST /mp/init — obtain a payToken (short-lived session token)
  3. Persist payToken in REQUIRES_NEW transaction (crash safe — see Pitfall 3)
  4. POST /mp/pay — initiate the actual merchant payment using payToken
Pitfall 7 — Orange correlation key is payToken, not txnid The Orange callback payload contains both txnid (Orange-internal) and payToken. Only payToken correlates back to a Payam transaction. Querying by txnid will return no match. This is a common integration mistake.

Token management

OAuth2 access tokens (consumer key + secret) are cached with TTL. On expiry or 401, the token is refreshed automatically.

Circuit breaker

@CircuitBreaker wraps provider calls. Domain exceptions (SubscriberInactive, PayTokenExpired) are in ignoreExceptions — they pass through without counting as failures. No fallbackMethod is defined; CallNotPermittedException propagates to the orchestrator and maps to HTTP 503. See Pitfall on circuit breaker fallback.

MTN MoMo Adapter

File: mtn/service/MtnMoMoPort.java, mtn/infrastructure/MtnMoMoClient.java

Initiation sequence

  1. Validate account holder (GET /v1_0/accountholder)
  2. POST /v1_0/requesttopay — async request. Returns immediately with an externalRef UUID.
  3. Persist externalRef (providerRef) in REQUIRES_NEW transaction before any further work
  4. Callback arrives at PUT /v1/callbacks/mtn/{externalRef}
INFERRED — MTN callback body structure The MTN callback is a PUT (not POST) with the external reference in the path. The body structure accepted by Payam is INFERRED from the adapter code and may differ slightly from the live MTN MoMo API specification.

Polling fallback

If no callback arrives within a configured window, a Quartz poller job queries GET /v1_0/requesttopay/{externalRef} and applies the same double-check transition logic.

Fraud Engine

File: fraud/service/FraudScoringService.java, fraud/service/VelocityCheckService.java

Four independent token bucket velocity checks backed by Redis (Bucket4j + Lettuce). Each bucket represents a sliding window of allowed requests per dimension:

DimensionBucket KeyPurpose
IP addressfraud:ip:{ip}Detect card-mill scripts from one origin
MSISDNfraud:msisdn:{msisdn}Detect repeated charges to same number
Applicationfraud:app:{tenantId}Detect compromised merchant credentials
Householdfraud:device:{fingerprint}Detect same device reusing different numbers

Exceeding any bucket threshold contributes to a fraud score. Above the configured score threshold, the payment is rejected (FraudException), a FraudEvent is published, and the payment.fraud.blocked.total counter increments.

INFERRED — Bucket window duration The token bucket window durations (e.g. 100 attempts per minute, per hour) are INFERRED to be configurable via FraudRule entities in the database. The exact default values were not confirmed from the migration files.

The buckets are distributed across JVM nodes because they live in Redis — the fraud engine is cluster-safe without coordination overhead.

Webhook Services

The webhook module handles both directions: inbound provider callbacks and outbound merchant notifications.

Inbound — WebhookDoubleCheckHandler

Fires via @TransactionalEventListener(AFTER_COMMIT). Receives a WebhookReceivedEvent after the dedup record commits, then calls the provider status API. Delegates terminal transitions to WebhookTransitionService — a separate Spring bean to preserve AOP proxy integrity (see Pitfall 4).

Outbound — WebhookDeliveryService

After a terminal transition, an outbound delivery is enqueued. The delivery is signed with HMAC-SHA256 using the tenant's webhook secret. The signature is sent in the X-Payam-Signature header (or equivalent).

Pitfall 5 — HMAC-SHA256 ≠ SHA-256 The outbound webhook uses javax.crypto.Mac (keyed HMAC), not DigestUtils.sha256Hex (plain hash). Both are present in the codebase. Confusing them would produce an unverifiable signature on the merchant side.

Retry policy: exponential backoff — 2^attempt minutes, capped at 60 minutes, maximum 5 attempts. Retries are driven by a Quartz WebhookDeliveryJob using the PostgreSQL JDBC job store (cluster-safe).

Fee Module

File: fee/service/FeeEvaluationService.java

Supports two rule types per tenant:

  • Fixed — flat amount regardless of payment amount
  • Percentage — configurable rate applied to payment amount

Rules are cached. The computed fee is stored on the Transaction record within TX2 of the orchestrator. Fee rules are managed by admin users.

INFERRED — Fee tiering Whether fee rules can be tiered by amount range is INFERRED — the service supports at least fixed and percentage. More complex banding was not confirmed.

Reconciliation Module

File: reconciliation/service/ReconciliationService.java

A scheduled job compares the internal ledger against the provider's daily settlement report. Discrepancies are stored in reconciliation_discrepancy and surfaced to admins. Reports are stored in reconciliation_report.

INFERRED — Provider report format How Orange/MTN deliver their daily reports (SFTP file, API endpoint, email attachment) is INFERRED. The reconciliation code reads a report entity but the ingestion mechanism was not confirmed.

L4 Concurrency & Transaction View

This level maps exactly where database transactions begin and end, which operations hold DB connections, which use Redis for coordination, and how concurrent requests are serialised.

PaymentOrchestrator — Intentionally NOT @Transactional

Pitfall 1 — Do not add @Transactional to PaymentOrchestrator.initiate() This method makes outbound HTTP calls that can take hundreds of milliseconds to seconds. Wrapping the whole method in a DB transaction would hold a HikariCP connection open for the duration of every provider call. With a pool of 25 connections and even moderate concurrency, the pool exhausts and new requests queue indefinitely. The design deliberately uses discrete TransactionTemplate blocks instead.

REQUIRES_NEW Transaction Blocks

Three locations use Propagation.REQUIRES_NEW — each for a specific reason:

LocationWhy REQUIRES_NEW
OrangeMoneyPort.persistPayToken() Commits payToken before the /mp/pay API call. If the JVM crashes after the call but before the outer flow completes, the payToken is already in the DB and the reconciliation job can resume. (Pitfall 3)
MtnMoMoPort.persistProviderRef() Same crash-safety rationale for MTN's externalRef.
WebhookTransitionService.applyFinalTransition() Fires from a @TransactionalEventListener(AFTER_COMMIT) handler where no transaction is active. Without REQUIRES_NEW, @Transactional would be a no-op (no existing transaction to join).

Pessimistic Write Locks

findByTransactionIdForUpdate() uses LockModeType.PESSIMISTIC_WRITE on every state transition. This prevents a race condition between the inbound provider webhook and the Quartz poller job both attempting to apply a terminal transition simultaneously.

Why publish inside a TransactionTemplate? The WebhookReceivedEvent is published inside a small write transaction. This ensures the event is written to the Publication Registry atomically with the dedup record. If the event were published outside a transaction and the process crashed, the dedup entry would exist (blocking replay) but the event would never be delivered.

Quartz uses the PostgreSQL JDBC job store (QRTZ_* tables). This makes it cluster-safe — only one node executes each job even with multiple Payam instances.

10 Developer Misunderstanding Traps

These are the areas most likely to cause bugs or incorrect assumptions by developers new to the codebase.

Pitfall 1 — PaymentOrchestrator is NOT @Transactional (intentional)

Trap Adding @Transactional to PaymentOrchestrator.initiate() would hold a HikariCP connection open across outbound HTTP calls to Orange/MTN (potentially seconds per request). With 25 pooled connections and moderate concurrency, the pool exhausts. The design uses discrete TransactionTemplate blocks (TX1–TX4) so connections are held only for milliseconds. Never add @Transactional to this method.

Pitfall 2 — Three redundant transitions in the orchestrator (state machine constraint)

Trap Lines ~241–261 of PaymentOrchestrator apply INITIATED→AUTH_PENDING→AUTHORIZED→PROCESSING in rapid succession. It looks like a bug or dead code. It is not — the state machine's allowedTransitions() only permits adjacent transitions. There is no direct INITIATED→PROCESSING path. A TODO acknowledges this may eventually be simplified by collapsing intermediate states for the orchestrator path.

Pitfall 3 — persistProviderRef uses REQUIRES_NEW (crash safety, not waste)

Trap MtnMoMoPort.persistProviderRef() and OrangeMoneyPort.persistPayToken() commit in separate REQUIRES_NEW transactions before the subsequent API call. This looks wasteful (a commit before the "real" work). It is intentional crash safety: if the JVM dies between the API call completing and the outer transaction committing, the providerRef is already in PostgreSQL. Reconciliation can find and resolve these transactions.

Pitfall 4 — WebhookTransitionService exists only for AOP proxy integrity

Trap WebhookDoubleCheckHandler delegates to a separate WebhookTransitionService bean for the actual state transition. This seems like over-engineering. Without it, if the transition method were called directly (this.applyFinalTransition()), Spring's AOP proxy would be bypassed and @Transactional would be silently ignored — the transition would run without a transaction. The extra bean is mandatory.

Pitfall 5 — Outbound webhook uses HMAC-SHA256, not SHA-256

Trap DigestUtils.sha256Hex() (plain SHA-256, no key) is used elsewhere in the codebase for the event log hash chain. Outbound webhook signatures use javax.crypto.Mac with HmacSHA256 (keyed hash). Using the wrong one produces a signature that merchants' verification code will reject. Always use Mac.getInstance("HmacSHA256") for webhook signing.

Pitfall 6 — FilterRegistrationBean(setEnabled=false) must not be removed

Trap ApiKeyAuthenticationFilter is declared as a @Bean so it can be injected into the TenantSecurityConfig filter chain. Without the paired FilterRegistrationBean(setEnabled=false), Spring Boot auto-registers it as a servlet filter for ALL requests, including the JWT admin paths. The admin chain would then require an API key on every request. The setEnabled(false) call must be present.

Pitfall 7 — Orange correlation key is payToken, not txnid

Trap The Orange Money callback payload contains both a txnid (Orange-internal transaction identifier) and a payToken. Payam correlates callbacks to its own transactions via payToken. Querying by txnid will find nothing. Any code that processes Orange callbacks must use payToken as the lookup key.

Pitfall 8 — Redis idempotency fallback is load-bearing

Trap The PostgreSQL fallback in IdempotencyService.checkAndReserve() activates when Redis is unavailable. Without it, a Redis outage causes every payment request to fail with an idempotency reservation error. The fallback uses INSERT ... ON CONFLICT DO NOTHING for atomicity. Do not remove this fallback as a "simplification."

Pitfall 9 — open-in-view=false changes lazy loading behaviour

Trap spring.jpa.open-in-view=false is set. This disables the Open Session In View anti-pattern, which means accessing an unloaded lazy association outside a @Transactional method throws LazyInitializationException immediately. The codebase compensates with JOIN FETCH in all repository queries that load associations. Adding a new entity relationship without a corresponding JOIN FETCH will cause runtime exceptions in non-transactional code paths (controllers, event listeners).

Pitfall 10 — UsernameNotFoundException maps to HTTP 200

Trap In ApiAdvice.java, UsernameNotFoundException is intentionally mapped to HTTP 200 OK (not 401). This is security hardening against username enumeration attacks — a valid and invalid username produce the same HTTP response. Code that checks for 4xx to detect auth failures will behave incorrectly. Treat the response body, not the status code, as the authoritative signal.
