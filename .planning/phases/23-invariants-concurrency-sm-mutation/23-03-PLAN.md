**TransactionBoundaryTest** (TXN-01 through TXN-04):
Extends `AbstractPayamE2ETest`. All 4 test methods in one class. Seeds tenant in `@BeforeEach`.

**TXN-01** `initRow_existsAtProviderCallTime()`:
- Already covered in detail in 23-01-PLAN.md (INV-09-TEST uses this exact pattern).
  TransactionBoundaryTest can delegate to the same WireMock RequestListener approach or
  simply assert that after a full payment flow, the INITIATED event exists in event log
  (the DB commit before provider call invariant is the same). If `InitBeforeProviderCallTest`
  already exists from plan 23-01, this test can verify the same property from a different
  angle: use `WireMock.getAllServeEvents()` to check that the first serve event for
  `/v1_0/requesttopay` happened after the transaction row was first inserted.
  Primary assertion: `AtomicInteger rowCountAtProviderCall.get() >= 1` using RequestListener.

**TXN-02** `exceptionAfterInit_doesNotRollbackInitRow()`:
- Seed tenant. Create a WireMock stub for POST `/v1_0/requesttopay` that returns 500.
  POST payment → expect a failure response (provider returned 500 → orchestrator marks FAILED
  or throws). After the response, assert:
  `SELECT count(*) FROM main.transaction WHERE idempotency_key = ? AND tx_status = 'INITIATED'`
  — this may return 0 if the orchestrator transitions immediately out of INITIATED on provider
  error. Check actual behavior: if the orchestrator catches the 500 and transitions to FAILED
  within the same call, the INITIATED row exists transiently but the final state is FAILED.
  The meaningful assertion is: `SELECT count(*) FROM main.transaction WHERE idempotency_key = ?`
  equals 1 (the row was not deleted/rolled-back; it exists in FAILED state). This proves that
  the INIT row persists even when the provider call fails.
  Assert `tx_status = 'FAILED'` (not rolled back to nothing).
  Assert event log contains `PAYMENT_FAILED` event (the row exists in the event log).

**TXN-03** `modulithEvent_firesAfterCommit()`:
- Register an `ApplicationListener<PaymentCompletedEvent>` (or the equivalent domain event class
  — check what event type WebhookTransitionService publishes after SUCCESS) as a `@TestConfiguration`
  bean that records the event in an `AtomicBoolean`. Drive payment to SUCCESS. Use Awaitility
  to assert the `AtomicBoolean` becomes true within 5 seconds.
  The key assertion is that the event fires at all (proving `AFTER_COMMIT` wiring works end-to-end).
  Check the event class name: search for `@TransactionalEventListener` in the codebase to find
  the published event type. If the event is `WebhookDeliveryRequestedEvent` or similar, use that.
  Alternative simpler approach: Assert that a webhook delivery row exists in `webhook_delivery_log`
  after SUCCESS (the `@TransactionalEventListener(AFTER_COMMIT)` handler writes this row). This
  indirectly proves the event fired after commit without needing a test listener bean.
  Use `Awaitility.await().atMost(5, SECONDS).until(() ->
    jdbcTemplate.queryForObject("SELECT count(*) FROM main.webhook_delivery_log WHERE ...",
    Integer.class) > 0)`.

**TXN-04** `redisNx_preventsDoubleReservation()`:
- This tests that two threads cannot both see "key absent" for the same idempotency key.
  Use a `CyclicBarrier` with 2 threads, same idempotency key, same tenant:
  ```java
  CyclicBarrier barrier = new CyclicBarrier(2);
  String sharedKey = UUID.randomUUID().toString();
  Future<ResponseEntity<PaymentResponse>> t1 = pool.submit(() -> {
      barrier.await(); return postPayment(sharedKey);
  });
  Future<ResponseEntity<PaymentResponse>> t2 = pool.submit(() -> {
      barrier.await(); return postPayment(sharedKey);
  });
  ```
  Collect both responses. Assert that both succeed (202) OR one succeeds and one returns
  the same transactionId (idempotency deduplication). Assert only 1 DB row exists.
  Assert `mtnServer.verify(1, postRequestedFor(...))` — only one provider call.
  This is a lighter version of CONC-01 focused specifically on the Redis NX+EX boundary.

each mutant restart spawns a full Spring context. The `targetTests` list only includes tests
that can run fast. `OrangeTimestampWatTest` is a pure unit test (no Spring context) and will
be fast. The E2E tests (`StateMachineLegalTransitionsTest` etc.) start a Spring context — for
PITest these may be slow. The `targetTests` should primarily point to `OrangeTimestampWatTest`
to prove the mutation infrastructure works. For the 5 remaining MUT-02 kills, the associated
E2E tests (`HashChainIntegrityTest`, `LedgerDoubleEntryTest`, etc.) serve as documentation
that the code paths are tested end-to-end; PITest with `targetTests` pointing to
`OrangeTimestampWatTest` is the minimum to prove MUT-01 configuration works.

Add `<timeoutConstant>10000</timeoutConstant>` (10 second per-mutant timeout) to prevent
hanging on Spring context startup. If tests time out, reduce `targetTests` to only
`OrangeTimestampWatTest` for the initial configuration.
